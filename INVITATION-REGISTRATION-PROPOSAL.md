# Admin Invitations and Member Registration Proposal

## Goal

Allow an administrator to generate a registration link for a prospective member.
The invite link opens the separate registration application on its own
subdomain. The applicant submits their details there, but no family or member
records are created until an administrator approves the application. Rejection
must leave no family or member records behind.

This document records the current implementation findings and a proposed
approach. It does not implement the proposal.

## Current implementation

### Backend invitation table

The `invitations` table in [`api-backend-php/database/schema.sql`](./api-backend-php/database/schema.sql)
currently represents a parent-to-parent invitation. It stores:

- `invited_by_member_id`, a required foreign key to `member_profiles`
- optional invite email and mobile
- a unique `invite_code`
- status (`pending`, `accepted`, `expired`, or `cancelled`)
- sent and accepted timestamps

There is no application-submission data, review status, rejection reason,
reviewing administrator, or link to a family created after review.

### Current APIs

The routes are registered in [`api-backend-php/api/routes.php`](./api-backend-php/api/routes.php):

- `GET /api/v1/invitations` lists invitations.
- `POST /api/v1/invitations` creates an invitation.
- `DELETE /api/v1/invitations/{id}` cancels a pending invitation.
- `GET /api/v1/invitations/{code}` validates an invite and returns public
  invitation information.
- `POST /api/v1/invitations/{code}/accept` accepts the invitation.

The existing create endpoint in [`api-backend-php/api/invitations/store.php`](./api-backend-php/api/invitations/store.php)
allows parent users as well as admins to create invitations. It requires an
authenticated user profile ID as inviter, which is incompatible with
standalone admin logins unless the ownership model is changed.

The current accept endpoint in [`api-backend-php/api/invitations/accept.php`](./api-backend-php/api/invitations/accept.php)
immediately creates a member profile and member login, marks the invitation
accepted, and issues member tokens. It does not create a family or wait for
admin review. That behavior does not meet the requested approval/rejection
workflow.

Invite codes currently expire seven days after creation. The validation and
expiry logic is in
[`api-backend-php/services/community-notifications.php`](./api-backend-php/services/community-notifications.php).

### Applications

The admin app has no invitation or registration-review feature. Its routes are
in [`kcdf-admin-app/src/app/app.routes.ts`](./kcdf-admin-app/src/app/app.routes.ts),
and its sidebar is in
[`kcdf-admin-app/src/app/layout/sidebar/sidebar.component.ts`](./kcdf-admin-app/src/app/layout/sidebar/sidebar.component.ts).

The separate [`kcdf-parents-app`](./kcdf-parents-app) currently has only its
home route in `src/app/app.routes.ts`; it has no invite-registration route or
registration form. It can host the public registration page, served from the
registration subdomain.

## Proposed workflow

1. An authorized administrator creates an invite in the admin app. The API
   generates a high-entropy, single-use code and returns a link using a
   configured registration-app base URL, for example:
   `https://register.example.org/register/{invite-code}`.
2. The recipient opens that link in the separate registration app. The app
   validates the code using a public API endpoint and displays the registration
   form only for an eligible, unexpired invite.
3. The applicant submits family details (including family name and address)
   and their personal details. The API stores a pending application linked to
   the invite. It does **not** create a family, member profile, family
   membership, or login at this stage.
4. An administrator reviews the submitted application from the admin app.
5. On approval, the backend uses a single database transaction to create a
   family, member profile, and family membership, and records the reviewer,
   decision time, and created record IDs. The family code is generated by the
   backend according to an agreed unique-code policy.
6. After approval, the applicant receives a separate account-activation link
   to set a password. This avoids collecting or storing a password for an
   unapproved registration.
7. On rejection, the backend records the reviewer, decision time, and optional
   reason. It creates no family, member profile, family membership, or login.

Approval must be idempotent: repeating an approval request must not create
duplicate records. Review transitions should be conditional on the application
still being pending.

## Proposed data model

Keep invite lifecycle separate from application review lifecycle:

- Invitation state: generated/pending, submitted, expired, or cancelled.
- Application state: pending review, approved, or rejected.

Two possible schema strategies are:

1. **Extend `invitations` with application fields.** This is a smaller initial
   migration, but mixes reusable link lifecycle with submitted application and
   review data.
2. **Add a separate `registration_applications` table linked to an invitation.**
   This better separates token/link state from applicant-submitted data and
   review decisions, and is the recommended design.

The separate application should store the submitted family/address and applicant
fields, its review status, submission/review timestamps, reviewing admin login
ID, rejection reason, and the resulting family/profile/membership IDs after
approval. Do not store passwords in the application.

For invite ownership, use the administrator's `user_logins.id` rather than a
required `member_profiles.id`, or use a nullable admin login reference while
preserving legacy member-inviter support. This allows standalone admins to
create invites and provides an auditable actor.

## Proposed API changes

- Admin-authenticated invitation create/list/cancel endpoints, restricted to
  the agreed admin roles.
- Public invite-validation endpoint that reveals only the information needed
  to render the registration page.
- Public registration-submission endpoint that atomically stores an application
  and consumes the invitation against duplicate/replay submissions.
- Admin-authenticated pending-application list and detail endpoints.
- Admin-authenticated approve and reject endpoints. Approval creates family
  records transactionally; rejection records a reason and creates no family or
  member records.
- A post-approval activation flow for setting the member's password.

The existing immediate-accept endpoint must not continue to create an account
through the new admin registration flow. The old parent-to-parent invitation
feature should either remain explicitly separate and retain its behavior, or
be migrated to the new model; that compatibility choice should be made before
implementation.

Update the OpenAPI document, migrations, backend tests, and deployment/API
documentation along with the endpoints.

## Proposed app changes

### Admin app

- Add an Invitations page to create and copy/share links and list/cancel invites.
- Add a Registration Applications review page with pending, approved, and
  rejected filters.
- Add an application detail/review view for family and applicant details,
  approve action, and reject action with a reason.
- Restrict navigation and backend authorization to the agreed admin roles.

### Registration app

- Add a public route such as `/register/:inviteCode`.
- Validate the invite on page load and show clear invalid, expired, cancelled,
  already-used, and submitted states.
- Collect applicant and proposed family details, validate them client-side for
  usability, and rely on server-side validation as authoritative.
- Submit the application without requiring an authenticated member account.
- Do not accept a password until the application has been approved; then use a
  separate, short-lived activation token to set it.

## Cross-subdomain configuration and security

- Configure a registration-app base URL per environment; never build links from
  an untrusted request `Host` header.
- Add the exact registration origin to the API CORS allowlist, and allow only
  the required methods and headers.
- Public registration endpoints must not require an admin/member JWT. They
  must validate high-entropy invite/activation tokens, enforce expiry and
  single-use state, rate-limit submissions, and avoid returning private inviter
  or account information.
- Store token hashes where practical; do not log raw tokens or passwords.
- Use HTTPS for the admin, registration app, and API in production.
- Notify the applicant of the decision without exposing review-only data.

## Decisions to confirm before implementation

1. **Who may create invites?** This proposal recommends admins only for the
   new registration workflow. The existing API also allows parent users.
2. **Which admin roles may invite and review?** For example, super-admin and
   program-manager, or another role set.
3. **Family membership values on approval:** which relationship (`father`,
   `mother`, `guardian`, or `child`) and access role (`primary`, `normal`, or
   `student`) should be created for the applicant? These roles affect access
   control and must not be inferred silently.
4. **Family-code policy:** format and uniqueness strategy for server-generated
   codes.
5. **Invite lifetime and resubmission:** retain the current seven-day expiry,
   and whether an applicant may resubmit after an administrator requests
   corrections.
6. **Existing invitations:** preserve the parent-to-parent invitation flow as a
   separate feature, or replace/migrate it to the admin registration flow.
7. **Registration subdomain and activation delivery:** the production URL and
   whether account activation is sent by email, SMS, or another channel.

## Recommendation

Implement the new approval process as a separate registration-application
workflow linked to invitations. Reuse the existing code-generation concepts,
but do not reuse the current “accept invite creates profile and login” behavior
for this flow. Keeping application data separate and creating family/profile
records only during an atomic approval transaction directly satisfies the
requirement that rejected applications leave no such records behind.
